Top bar — redesign options

The element set is now stable, so this sheet compares common web top-bar patterns for how naturally they absorb the next item — a new public view, a signed-in-only view, a new action — without a layout rewrite. Every option renders the exact same element inventory; only arrangement and affordances change.

ELEMENTS  ·  brand (OpenBengaluru / what-would-you-change)  ·  public views: Discover, Contribute, Tutorials  ·  gated views: Dashboard (signed in), Admin (admin)  ·  auth: Google sign-in / signed-in chip  ·  actions: Export area, Submit a sim (primary)

A

App-shell nav bar

Inspiration: Linear, Stripe, GitHub, Notion. Brand left, plain nav links directly after the brand, actions pinned right. New views are appended to the nav list; a link is one config entry, and overflow (if ever needed) is a natural "More" tail.

  • Extensibility: nav is a flat config list {id,label,visible(state)} — a new view is one entry; the underline-indicator pattern does not run out of room as fast as a segmented control.
  • Auth degrades gently: Dashboard/Admin appear as links when entitled, or fold into the avatar menu (variant shown right).
  • Export area stays a labeled ghost action — it is a map utility, so it reads better as text than as an icon.
  • Risk: with brand + tagline + 5 links + 4 right actions the bar is full at ~1000px; needs a wrap/overflow rule (see notes).
  • Note: the two signed-in states can be combined — Dashboard/Admin as nav links and the avatar menu as the account surface only (sign out). Pick one.

VERDICT — strongest long-run shape; the one most product sites converge on. Gated items either join the nav or the menu, both cheap.

B

Centered segmented pill

Inspiration: Vercel dashboard, Figma file switcher, Railway. The current layout kept, restyled: the segmented control becomes a soft pill with a raised active thumb. Familiar to the app today; the cheapest change that still looks current.

  • Extensibility: same flat nav config as A; the pill grows horizontally — fine to ~6 items, then cramped.
  • Least churn: keeps the app's current three-zone mental model and the existing .viewtoggle markup (restyled), so tests/CSS deltas stay small.
  • Centered nav + pinned actions reads "product tool" — good when Discover stays the hero view.
  • Risk: centered controls are the first thing to break on narrow screens — they cannot wrap gracefully; needs a breakpoint decision sooner than A.
  • Risk: admin state (5 segments) already fills the pill; one more view forces the overflow question.

VERDICT — best if you want a visual refresh with minimal structural risk; extensibility ceiling is lower than A.

C

Slim header + tab strip

Inspiration: YouTube, Stripe docs, Atlassian. Row 1: brand, auth, actions. Row 2: view tabs. The most room of any option — but the map already lives under a top bar, so this costs vertical map space.

  • Extensibility: unlimited — the tab strip scrolls/shrinks independently of the action bar; the two concerns never fight for width.
  • Clear separation: "where am I" (tabs) vs "what can I do" (actions) never compete in one row.
  • Cost: ~40px of permanent vertical space taken from the map — the app's core surface. On short laptop screens this is a real tax.
  • Feel: reads "content site / docs", less "map tool".

VERDICT — most extensible, but the map-space tax and content-site feel make it the weakest fit for a map-first product.

D

Compact utility bar + overflow menu

Inspiration: Google Maps header, Figma toolbar, Slack. Brand left; primary nav as compact links; everything secondary (Export area, later: about, help, settings) lives behind one overflow menu. The most aggressive decluttering.

  • Extensibility: the overflow menu absorbs any number of secondary actions with zero layout cost — the strongest "add things later" story for actions.
  • Calmest bar: 2 buttons + menu visible at all times; brand tagline drops, bar can go shorter.
  • Risk: Export area becomes discoverable only inside the menu — it is a workflow entry (draw a bbox, download a net), so hiding it may hurt usage.
  • Tagline loss: "WHAT WOULD YOU CHANGE?" is the project's voice; dropping it is a brand decision, not a layout one.

VERDICT — best raw extensibility for actions; the Export-area discoverability tradeoff is the one thing to weigh. A/D hybrids work (keep Export as ghost, overflow for the rest).

§

Shared primitives (any option)

Whatever layout wins, these are the extensible building blocks the implementation should ship — each is data-driven, so future items slot in without new markup.

NAV CONFIG (PURE DATA)

[{id:'discover',label:'Discover',
 show:s=>true},
 {id:'dashboard',…
  show:s=>s.user&&s.me},
 {id:'admin',…
  show:s=>s.user&&s.me?.isAdmin}]

Ordered list of {id, label, visibility predicate} driving whichever nav affordance wins. Adding a view = adding an entry, in the component file or the store.

AVATAR MENU

Signed-in chip → dropdown: identity header, gated links (Dashboard/Admin if they move here), sign out. Replaces the "SIGNED IN AS name [Sign out]" inline row; shows the Google photo when present.

PRIMARY CTA

Exactly one accent-filled button per bar, always the last right element. "Export area" and auth become ghost/icon affordances so the hierarchy survives new actions.

OVERFLOW MENU

⋮ / “More”

Generic item-list menu (same component as the avatar menu body). Absorbs secondary actions and, at small widths, nav links that no longer fit.

RESPONSIVE RULE (ALL OPTIONS) — one breakpoint: below ~820px the nav (links or pill) collapses into the overflow menu, leaving brand + avatar + CTA; the bar never wraps to two lines. Decide once, reuse for every future item.
